### 14.52 持续区域技能的三种形态

**先问一句话，答案决定形态**：*一个目标站在这片区域里，会被判定几次？*

| 答案 | 形态 | 实证类 |
|---|---|---|
| 每个离散作用点各判一次 | **A 离散多点** | `SwordArrayLayout` / `SwordArrayEntity` / `SwordPrisonSpell` |
| 每个目标被冲击波扫过一次 | **B 单中心 + 波前** | `PalmBlackHoleEntity` / `PalmBlackHoleTimeline` / `PalmBlackHoleSpell` |
| 每 N tick 判一次（站着就一直掉） | **C 几何力场** | `ThreeEnclosuresFieldEntity` |

三种形态各自解决的是**不同的语义**，写成同一种就必然出错（见 ⑩ 的两个反例）。

### ① 三形态对照表（先看这张表再动手）

| 维度 | A 离散多点 | B 单中心 + 波前 | C 几何力场 |
|---|---|---|---|
| 判定对象 | 每个剑点 | 每个目标（一生一次） | 每个目标（每 N tick） |
| 去重手段 | `BitSet` 位图（哪个点被消耗） | `Set<UUID> hitTargets`（谁被扫过） | 无——靠区域判定天然重复 |
| 时间源 | `gameTime - startedAt` | 自增 synched `AGE` | `Entity.tickCount`（`f_19797_`） |
| 必须同步的状态 | seed / level / radius / startedAt ＋ 位图 | AGE / START_HEIGHT / RELEASE_YAW / hitTargets | DATA_RADIUS / DATA_ANGLE / DATA_EXPANDING |
| 客户端拿到什么 | 参数，自己重建布局 | AGE + 起始高度，自己插值 | 半径 + 角度，直接画 |
| 详见 | §14.51 | 本文件 ③④⑤⑥ | 本文件 ⑦ |

**A 与 B/C 的根本差别**：A 的状态量随「点」增长（N 个点 → N 位），B/C 的状态量随「目标」增长（M 个目标 → M 个 UUID）。
**所以 A 用位图，B 用 Set，C 什么都不用**——选错容器，要么漏判，要么存档里塞进一堆无用 NBT。

### ② 形态 A 的补充：施法端与实体端的常数必须共享（实证）

§14.51 记了「常量与字面量重复」的坑，这里补上**第三处**——它在**施法端**，不在实体里：

```text
环间距的 3 处硬编码（行号仅作定位线索）：
  ① 布局类具名常量 RADIUS_STEP = 1.2        ← 唯一被别处引用的那份
  ② 布局类内部算环半径：innerRadius + ring * 1.2    ← 字面量
  ③ 施法类 tooltip 计数函数：innerRadius + ring * 1.2 ← 字面量（第三处）
```

施法类里有个 `public static` 的「剑数计数」函数，签名是 `(spellLevel, targetHalfWidth)`，
被 tooltip 的 `getUniqueInfo(spellLevel, caster)` 调用，语言键形如 `ui.<命名空间>.projectile_count`。

- **现象**：改 `RADIUS_STEP` 只改到实体构造，tooltip 的数量不变 → 玩家看到的剑数和实际落地的剑数对不上。
- **根因**：同一份「环间距」在 3 处独立硬编码，其中 2 处是字面量，改常量只影响 1 处。
- **修法**：把环间距收成唯一入口，三处都调它：

```java
// SwordArrayLayout
public static double radiusStep() { return RADIUS_STEP; }
public static double ringRadius(double innerRadius, int ring) { return innerRadius + ring * radiusStep(); }
```

- **不修的后果**：数值平衡调一次，UI 与实际不符一次；且因为 `getTotalSwordCount` 是 public static，
  别处（HUD、攻略、命令）也会跟着显示错的数。

### ③ 形态 B：时间轴先抽成纯函数类，再写实体

`PalmBlackHoleTimeline` 53 行、全 `static`、**零字段**，实体 `PalmBlackHoleEntity` 362 行只负责同步/存档/伤害/粒子/音效。

```text
时间轴纯函数类的常量组（全部 static final，按语义顺序）：
  上升段结束 tick | 下坠段结束 tick | 冲击 tick（= 施法总时长）
  波前铺开时长 20 tick | 爆炸半径 16 格
  脉冲起始 tick | 脉冲间隔 20 tick | 脉冲半径 10 格
```

- **为什么必须抽出去**：时间轴要同时被服务端（判定）、客户端（渲染）、可能的预览/HUD 读取。
  混在实体里就只能靠 `entity.tick()` 的副作用，任何「不推进 tick 也能算」的场景（暂停预览、编辑器、单测）全废。
- **伤害只给公式，不给数**：两个伤害函数都含 `maxHealth`，与目标血量绑定：

```text
脉冲伤害 = 2.0 + 目标血量 × 0.1
爆炸伤害 = 10.0 + 目标血量 × 0.2
```

**别把「2.0 + 0.1×血量」写成「每跳 2 点」**：对高血量 Boss 两者差一个数量级，写死数字就是不可复现的假精确。

### ④ 形态 B：波前扫掠——必须用「上一 tick 半径 → 本 tick 半径」区间

```text
伪代码（保留原判定顺序）：
if 年龄 >= 冲击 tick:
    上一 tick 半径 = 时间轴.波前半径(年龄 - 1)
    本 tick 半径   = 时间轴.波前半径(年龄)
    取 [当前位置 ± 半径] 的盒子（水平 inflate 半径+1，竖直 4 格）内的所有生物
    对每个目标：
        if 是敌人 && 目标 UUID 不在命中集合内:
            距离 = 水平距离（丢掉 Y 分量）
            if 时间轴.是否跨越波前(距离, 上一 tick 半径, 本 tick 半径):
                命中集合加入目标 UUID
                造成 爆炸伤害(目标血量)
                if 命中成功: 按「1.1/距离, 0.45, …」施加冲量并置 hasImpulse
```

```text
波前半径(年龄) = 16 × clamp((年龄 − 340) / 20, 0, 1)
是否跨越波前(距离, 上一半径, 本半径) =
        距离 >= max(0, 上一半径 − 0.8)   &&   距离 <= min(16, 本半径 + 0.8)
```

四条设计点，每一条去掉都会出事故：

1. **不能用「在半径内就判」**：那等于每 tick 都命中圈内所有目标 → 语义从「冲击波扫过一次」变成「力场持续伤害」，
   伤害随停留时间线性增长，站桩的玩家直接被秒。
2. **不能用严格区间 `(previous, radius]`**：目标每 tick 在动（击退、冲刺、被牵引），
   高速目标一 tick 能跨过整个区间，严格区间会整段漏判。`0.8` 是**双向容差**（下界 `previous - 0.8`、上界 `radius + 0.8`）。
   **`0.8` 的来历与边界**：`0.8F` 是**独立字面量**；数值上恰等于 `BLAST_RADIUS / WAVE_TICKS`（16/20），
   但源码未由这两个常量派生，改常量不会带动容差——**必须一起改**。
   边界：常规步行/冲刺单 tick 位移远小于 0.8，容差够用；但**击退、鞘翅滑翔、高速弹射物、
   被其他模组位移法术推走的场景，单 tick 位移可到数格**，仍会整段跳过容差带（扫掠窗口总宽 = 扩张量 0.8 + 两侧容差各 0.8 = 2.4 格，
   位移超过 2.4 格/ tick 即可穿透）。两种修法：① 按本技能可能出现的最大单 tick 位移放大容差；
   ② 更彻底——记录目标上一 tick 位置，改判「上一位置 → 当前位置的线段是否与环带相交」（线段扫掠），
   此时容差只需覆盖数值误差，与速度无关。
3. **容差区间必然跨 tick 重叠 → 必须配 `hitTargets` 去重**：同一目标会在相邻两 tick 都落进区间，
   不去重就是双倍伤害。容差越大，越依赖去重。
4. **上界必须 `min(16.0, ...)`**：`radius` 在 20 tick 内从 0 涨到 16（`WAVE_TICKS`），
   `radius + 0.8` 会短暂超过 `BLAST_RADIUS`，不 clamp 就会打到半径 16 之外的目标，
   且与视觉上的波纹半径不符（玩家看到波没到，自己却掉血）。

**盒子的 `+1.0F` 与 `4.0`**：查询盒比波前半径大 1 格（容差 0.8 的余量），竖直方向只给 4 格——
波前是地面横扫，给太高会误判空中的目标。**距离只算水平分量**（`offset.multiply(1, 0, 1).length()`），
否则空中的目标永远「距离很远」，永远不会被扫到。

### ⑤ 形态 B：命中集合必须存档，伤害必须绕过无敌帧

**存档**（不存 → 读档后同一次爆炸把同一目标再打一遍）：

```text
伪代码（存档字段清单）：
if 施法者UUID 非空: 写入 UUID
写入 同步年龄 / 起始高度 / 释放朝向
遍历 命中集合，把每个 UUID 包成一个 CompoundTag，塞进 ListTag，写入存档
```

`hitTargets` 是**推不出来的状态**（依赖运行时谁站到了波前上），必须入档；`waveRadius` 能由 `age` 推出来，不必存。
这条和 §14.51 的「位图必须同步、坐标不必」是同一条原则的两种形态。

**绕过无敌帧**：

```text
伪代码（「无视无敌帧」的三步）：
保存 = 目标的无敌帧剩余 tick        // 原版 invulnerableTime 字段
目标的无敌帧剩余 tick = 0
try:
    命中结果 = 底层伤害入口.结算(目标, 伤害, 伤害源)
finally:
    if 命中结果 == false:
        目标的无敌帧剩余 tick = 保存值    // ← 只在没打中时恢复
返回 命中结果
```

- **为什么置 0**：原版 `hurt()` 有约 10 tick 无敌帧。脉冲间隔 20 tick、爆炸与波前在**同一段** tick 里，
  同一目标可能在极短时间内被多次结算 → 不置 0 后半段直接被吞，表现为「Boss 大招打空」。
- **为什么失败要恢复**：被护盾/无敌/友伤规则挡掉时，不该顺手把目标的无敌帧清零，
  否则等于替攻击方把目标的保护拆了，下一次随便什么伤害都能进。
- **`finally` 而不是顺序语句**：`applyDamage` 抛异常时也要恢复，否则目标永久失去无敌帧。

**双伤害源拆半**（`applyPulse`）：

```text
伪代码（双伤害源拆半）：
半伤 = 脉冲伤害(目标血量) * 0.5
已伤 = 通用源结算(施法者, 目标, 半伤)            // 不带法术学派
if 权威血量.战斗中存活(目标):
    已伤 |= 无视无敌帧结算(目标, 半伤, 法术自带的伤害源)   // 带法术学派归因
```

- 一半走 `hurtWithVoid`（`new DamageSource(target.damageSources().<通用源>.getType(), this, caster)`），
  一半走 `getDamageSource(this, caster)`（带法术学派归因）。合计才是 `pulseDamage`。
- **可见的设计意图**是「把归因拆成两半」：一半不带法术学派，一半带。
  **具体抗性/减伤表现取决于第三方属性系统，本库不下结论**——换目标模组必须实测，别照抄结论。
- **`combatAlive` 再判一次**：第一路可能已经打死目标，第二路必须跳过，否则对尸体结算伤害会触发死亡逻辑二次执行。

### ⑥ 形态 B：生命周期绑定施法者（条件组 + 收尾窗口 + 取消清理）

```text
伪代码（tick 顶部：先判施法者有效，再判是否推进年龄）：
if 施法者 is 本 Boss 实体类型 且 战斗中存活 且 处于战斗 且 处于二阶段 且 未在转场:
    年龄 = 同步年龄字段 + 1
    if 年龄 >= 339 || (施法者.正在施法() && 施法者.当前法术ID == 本法术ID):
```

- **age 只在「施法中」推进**（`age >= 339` 之后例外）：施法被打断 → 条件不成立 → 走 `discard()`，
  区域立刻消失，而不是留一片黑球继续打人。
- **`age >= 339` 是收尾窗口**：`PalmBlackHoleSpell.castTime = 340`，爆炸发生在 340，
  施法在 340 结束后必须允许它跑到 `age > 368` 才 `discard()`（波前在 340..360 铺完，再留 8 tick 给粒子）。
  没有这个窗口，施法一结束仪式就自己没了，爆炸永远看不到。
- **条件组要全判**：`combatAlive`（死了）、`isBattleActive`（脱战）、`isPhaseTwo`（换阶段）、
  `isTransitioning`（转场中）。漏任何一个都会出现「Boss 死了但黑球还在打人」或「转场动画里黑球穿模」。

**取消施法必须清理已生成的实体**：

```text
伪代码（施法完成回调里的取消清理）：
在 服务端施法完成回调(level, spellLevel, caster, magicData, cancelled) 中：
    if cancelled:
        取 level 内所有 本仪式实体类，包围盒 inflate 32 格，过滤 属于该施法者
        逐个 discard()
```

- 实体是在 `onServerPreCast` 里生成的（**早于施法完成**），取消时必须有回收路径。
- tick 里的自灭条件已能兜住大多数情况（`caster.isCasting()` 为 false → discard），
  显式扫一遍是为了覆盖 **`age` 已过 339 的残体**（它靠收尾窗口活着），以及一次施法生成多个实体的情况。
- **`belongsTo(caster)` 必须双端实现**：客户端比 `CASTER_ID`（synched int），服务端比 `casterUuid`。
  只比 UUID → 客户端拿不到 UUID 判不了；只比 int → 存档重载后 id 复用会误杀别人的仪式。

### ⑦ 形态 C：几何力场——用「区域判定」代替「命中记录」

**双层几何判定，少一层就错**：

```text
伪代码（双层判定，缺一层即失效）：
在高度区间内 = 目标.Y >= 场底Y 且 目标.Y <= 场顶Y
在区域内     = 在高度区间内 且 点在多边形内(目标.X, 目标.Z, 半径)
if 在区域内:
    施加 缓慢 效果（时长 12 tick，等级 0，粒子/图标 开）
```

- **只判水平**（`isInsideTriangle`）→ 从高空飞过也被判在区域内。
- **只判竖直** → 全场命中。
- 水平用**三角形/多边形**而不是圆：视觉上是棱柱，判定必须与视觉一致，否则「看着在柱子外面却掉血」。

**贴墙判定**：

```text
伪代码（贴墙判定，注意两个阈值不同）：
靠近上下端面 = 目标.Y >= 场底Y − 0.75 且 目标.Y <= 场顶Y + 0.75
if 靠近上下端面:
    到墙距离 = 到多边形边界的距离(目标.X, 目标.Z, 半径)
    贴墙 = (不在区域内) 或 (到墙距离 <= 0.35)        // 0.35 = 墙厚
    if 贴墙:
        if 不在区域内 或 到墙距离 <= 1.1: 向中心推挤
        if 实体.tickCount % 10 == 0: 结算伤害
```

- **`!inside` 也算贴墙**：区域**外**但紧贴墙的目标也要推回中心，否则玩家站在柱子外面就能白嫖——
  「围栏」的语义是关住，不是「外面随便站」。
- **推与伤的两个阈值不同**（`1.1` vs `0.35`）：推的判定更宽，让「快出界」的也被吸回来；伤害只在真正贴墙时结算。

**双重节流陷阱（本节最容易踩的一条）**：

```text
双层节流的实际结构：
  tick 顶层：      if 实体.tickCount % 4 == 0 → 调用 场效果()
  场效果() 内部：  if 实体.tickCount % 10 == 0 → 结算伤害
```

**实际伤害间隔 = lcm(4, 10) = 20 tick，不是 10 tick。** 改 `DAMAGE_INTERVAL` 也不一定得到你想要的间隔
（改成 8 → lcm(4,8)=8；改成 6 → lcm(4,6)=12）。**修法**：把伤害节流提到 tick 顶层，只留一层 `%`，
`applyFieldEffects` 只做「施加效果 + 推挤」，不再自带周期判定。

**音效必须按 UUID 冷却**：

```text
伪代码（按 UUID 冷却的音效）：
if 冷却表 不含 目标.UUID:
    播放音效(位置=目标所在方块, 类别=敌对, 音量 0.65, 音高 0.75 + 随机 * 0.25)
    冷却表[目标.UUID] = 16
```

- **为什么**：贴墙的目标每 4 tick 就被判一次，直接放音效就是连续叠放 → 音量爆掉、客户端卡顿。
- **为什么用 `Map<UUID, Integer>` 而不是位图**：每个目标需要**独立倒计时**；位图只能记「有没有」。
  每 tick 全表递减 + `removeIf(value <= 0)`，表大小 = 区域内贴墙目标数，很小。
- **`0.75F + random * 0.25F` 的音高抖动**：同 tick 多个目标贴墙时不至于叠成同一个音高。

**收缩曲线三段（`currentRadius`）**：

```text
伪代码（半径曲线，三段）：
当前半径(年龄):
    扩张 = 同步布尔字段
    if 年龄 <= 30: 返回 (扩张 ? 2.15 : 10.0)                       // ① 预警期：不缩
    进度 = clamp((年龄 − 30) / 180, 0, 1)                          // ② 30..210 线性
    返回 lerp(进度, 扩张 ? 2.15 : 10.0, 扩张 ? 10.0 : 2.15)
```

- **① 预警期不缩**：`TELEGRAPH_TICKS = 30` 内半径固定，给玩家反应时间；一生成就开始缩等于无预警秒杀。
- **② `Mth.clamp` 到 `[0,1]`**：不 clamp 的话，`age > 210` 之后 `lerp` 会越过终点继续走（收缩分支继续小于 `2.15`、扩张分支继续大于 `10`）；负半径要 `age ≈ 260` 才到，而 `:88` 的守卫是 `tickCount <= 250`，实际跑不到。
- **③ 用 `DATA_EXPANDING` 而不是两个类**：收缩与扩张是同一条曲线取反，一个布尔字段就够；两套类会让同步与存档双份维护。
- **半径每 tick 同步**（`:90` `entityData.set(DATA_RADIUS, radius)`）：客户端要用它画墙；
  这是「同步参数」，与 §14.51 同原则。**`DATA_ANGLE` 每 tick `+ 0.006`（`:91`）也由服务端推进**——
  客户端自己转的话，两侧角速度/帧率不同必然漂移。

**⚠ 同一个「常量集中定义但没被使用」问题，形态 C 也有——而且更彻底**：

```text
:41-48 连续定义 8 个 static final 常量（逐个清点见下表）：
预警 tick / 收缩 tick / 收尾保持 tick / 总 tick
墙厚 / 伤害间隔 / 音效间隔 / 减速刷新间隔
```

**这 8 个常量的符号引用数全部为 0**（逐个 `grep` 常量名，除定义行外零命中）。区别只在「值有没有被抄成字面量」：

| # | 常量 | 定义处 | 常量名引用数 | 实际用的字面量 | 判定 |
|---|---|---|---|---|---|
| 1 | `TELEGRAPH_TICKS = 30` | `:41` | 0 | `:113` `if (age <= 30)` | 值被绕过 |
| 2 | `SHRINK_TICKS = 180` | `:42` | 0 | `:116` `/ 180.0F` | 值被绕过 |
| 3 | `FINAL_HOLD_TICKS = 40` | `:43` | 0 | **无任何同值字面量** | **死常量（连值都没用）** |
| 4 | `TOTAL_TICKS = 250` | `:44` | 0 | `:88` `&& this.tickCount <= 250` | 值被绕过 |
| 5 | `WALL_THICKNESS = 0.35F` | `:45` | 0 | `:135` `<= 0.35F` | 值被绕过 |
| 6 | `DAMAGE_INTERVAL = 10` | `:46` | 0 | `:141` `% 10 == 0` | 值被绕过 |
| 7 | `SOUND_INTERVAL = 16` | `:47` | 0 | `:150` `put(..., 16)` | 值被绕过 |
| 8 | `SLOW_REFRESH_INTERVAL = 4` | `:48` | 0 | `:92`、`:96` `% 4 == 0` | 值被绕过 |

**统计口径**：上表 **8 行 = `:41-48` 那 8 个常量，一个不多一个不少**。
「7 个值被绕过 + 1 个死常量（`FINAL_HOLD_TICKS`）」——这两个数加起来正好是 8，
早期版本把 `FINAL_HOLD_TICKS` 从表里漏掉、却让正文点名它「完全未被引用」，属于「表格没验证正文」。

另有两个**表外常量**（`:38-39` `INITIAL_RADIUS = 10.0F` / `FINAL_RADIUS = 2.15F`），
同样 0 引用、值被 `:114` / `:117` 的 `10.0` / `2.15` 绕过——它们不在那 8 个里，单列在此，**不要并进上表计数**。

> **本节常量总数 = 10**，边界如下，避免「说 8 个、实际数到 10 个」：
> - **表内 8 行** = `:41-48` 的 8 个 `static final`（上表逐行对应，一个不多一个不少）；
> - **表外 2 个** = `:38-39` 的 `INITIAL_RADIUS` / `FINAL_RADIUS`（只写在本段文字里，**不进表、不计入 8**）。
> 数表格行数得 8 是对的；数整节常量得 10 也是对的——两者不冲突，因为口径不同。

改任何一个常量都不会生效。**A（`1.2` 三处）、B（`240`/`260`/`340`/`368` 见下）、C（上表）三个类都有这个问题**——
这不是个案，是「先写常量、再图快写字面量」的通用退化模式。**自查方法**：
`grep` 每个 `static final` 常量的**数值**，看还有没有同值字面量出现在调用处。

形态 B 的具体落点（`PalmBlackHoleTimeline` 定义了常量，`PalmBlackHoleEntity` 却用字面量）：
`:90` 的 `339`、`:93` 的 `240`/`260`（对应 `WARNING_START_TICK`/`TOP_TICK`）、`:106` 与 `:125` 的 `340`（`IMPACT_TICK`）、
`:148` 的 `368`（无对应常量）、`:225` 的 `float radius = 10.0F`（`PULSE_RADIUS`）。
**改时间轴常量在实体里完全不生效**——必须两处一起改，或把实体里的字面量全部换成常量引用。

### ⑧ 三形态的时间源对比（最容易被忽略的一条）

| 时间源 | 区块卸载/暂停时 | 恢复后 | 适合的语义 |
|---|---|---|---|
| A `gameTime - startedAt` | **继续走**（`gameTime` 不停） | 一次跳过整段 | 「到点必须结束」的限期效果 |
| B 自增 synched `AGE` | 冻结（实体不 tick） | 从冻结处继续，**总时长变长** | 与施法者绑定、中断即作废的仪式 |
| C `Entity.tickCount` | 冻结 | 同上 | 同上，且不需要额外同步字段 |

- **A 的后果（由实现可推出，未实测）**：`getArrayAge()` 的实现是「当前 `gameTime` 减去起始 `gameTime`，
  夹到 int 正区间」，
  区块卸载 60 tick 再回来会一次 +60，`tickContacts` 只跑一次 →
  这 60 tick 里本该结算的剑点伤害全部丢失（`plantedAge % 8` 的节拍点在跳过区间里没人执行），
  还可能直接越过 `layout.lifetime()` 当场 `discard()`。
  注意节流是 `plantedAge % 8`，回来后会自然对齐到下一个 8 的倍数（最多再等 8 tick），**不会永久错位**；
  丢的是「跳过的那些 tick 的伤害总量」。
  玩家看到的是「阵直接消失、一点伤害没有」。要保证**伤害总量**就别用 `gameTime`。
  **两条可选修法**（按你要保的语义二选一，不要同时上）：
  ① **要伤害总量** → 换成 `tickCount` 驱动（自增 `AGE` 或实体 `tickCount`），
     并把「总时长」显式写成常量；卸载期间冻结、回来继续，总量不丢，代价是效果整体延后。
  ② **要准时结束** → 保留 `gameTime`，在「`age` 越过 `lifetime`」的那一 tick 里做一次**补偿结算**：
     按 `% 8` 的节拍算出被跳过的次数 `skipped = (age - lastProcessedAge) / 8`，
     一次性补 `skipped` 次，再 `discard()`。
     **补偿结算必须带单次上限（建议 `min(skipped, 8)`，即最多补一个周期）**——
     **不加则卸载后回归时会一次性结算全部积压（推论，未实测）**；
     补偿次数与卸载时长成正比，长时间卸载后回归的结算量没有上界。

> **置信度口径（与 14b §14.51 统一）**：`getArrayAge()` 的**实现**是核对过的事实；
> 「卸载 N tick → 一次 +N → 丢掉这 N tick 的伤害总量」这个**后果**是**由实现推出、未实测**。
> 14b §14.51 引用同一机制，此前用「实测」语气，现已改成与本节一致的「未实测」。
> 要把它当结论用，先跑一次「卸载区块 → 重新加载」观测。

- **B/C 的后果**：卸载期间不推进，回来继续 → 玩家把 Boss 拉出加载区再回来，仪式还在原地。
  对「施法者中断即作废」的仪式，这反而是对的（`isCasting()` 不成立会 discard）。
- **判据**：**要保证「准时结束」用 `gameTime`，要保证「总量/时长」用 `tickCount` 或自增**。
  **绝对不要在一个技能里混用**——一半 `gameTime` 一半 `tickCount`，卸载一次就永久错位（§14.30 区块加载，`14f-lifecycle-chunk.md`）。

### ⑨ 三形态共同的四条（把硬纪律落到本节）

1. **客户端只视觉，服务端只判定**：A 走 `tickVisuals` / `tickContacts` 分叉；
   B 走 `if (level instanceof ServerLevel server)`；C 走 `if (!level.isClientSide())`（§14.51 ⑦）。
2. **固定间隔结算，不是每 tick**。A / C 的节流位置不同，别混着记：
   - **现状（A）**：节流在**每支剑自己的相对年龄**上（判定条件是
     `plantedAge > 0 && plantedAge <= plantedLifetime && plantedAge % 8 == 0`）；
     实体侧 `tickContacts(age)` **每 tick 都跑**，**实体层没有节流**。
     因此卸载跳过 60 tick，丢的是这段区间的伤害总量，恢复后会在 ≤8 tick 内自然对齐到下一个 8 的倍数。
   - **假设（A，不要这么做）**：如果在实体层再加一层 `% N`，会与剑点的 `% 8` 取 lcm，
     实际间隔变成 `lcm(N, 8)`，与两者都不等（与 ⑦ 的 lcm 陷阱同类）。
   - **现状（C）**：**已经**是两层——`% 4` 外层（`:92`、`:96`）套 `% 10` 内层（`:141`），
     实际伤害间隔 `lcm(4,10)=20`，这是**现存缺陷**，修法见 ⑦。
3. **生命周期绑定施法者，任一条件失效即 `discard()`**：B 判 4 条件、C 判 `combatAlive(caster) && 同 level && tickCount <= TOTAL_TICKS`。
4. **存档只存「推不出来的量」**：A 存位图、B 存 `hitTargets` + `AGE`、C 存 `Expanding`（半径由 age 重算）。

### ⑩ 选型判据（一句话版）

- **「一片区域持续惩罚」**（火墙、毒雾、冰柱围栏）→ **C**。最省：零命中记录，纯几何判定 + 固定间隔。
- **「一次爆发命中一片」**（冲击波、新星、爆炸）→ **B**。波前 + `hitTargets`，命中次数精确可控。
- **「多点、可见、逐点消耗」**（剑阵、箭雨、地刺）→ **A**（§14.51）。
- **需要「N 个独立可消耗单元」或「视觉上是离散物件」** → **只能 A**。B/C 无法表达「这把剑已经用掉了」。

**两个必错的反例**：

- **把 B 写成 C**：波前语义用「在半径内就判」实现 → 站在中心的目标每 tick 都被打，
  伤害随停留时间线性增长，Boss 大招变成秒杀。**症状**：只有站在正中心的人瞬间死，外围的人没事。
- **把 C 写成 B**：力场用 `hitTargets` 去重 → 玩家进区域被打一次，之后站在里面再也不掉血。**症状**：力场「只有第一下有效」。

### ⑪ 形态 B 的包围盒与剔除（与 §14.51 ⑧ 同一原则，参数不同）

```text
伪代码（覆写包围盒与剔除距离）：
包围盒():
    上界Y = max(40, 同步的起始高度 + 16)
    返回 AABB(位置 ± (32, -16..上界Y, 32))
是否在该平方距离内渲染(距离平方): 返回 距离平方 < 16384   // 16384 = 128²
```

- **横向 ±32**：波前半径到 16，粒子环外扩到 2 格，模型缩放 `MAX_MODEL_SCALE = 3.2`，留余量。
- **纵向 `max(40, START_HEIGHT + 16)`**：模型从高空落下（`dropHeight`），起始高度是运行时算的，
  **必须用 `max` 兜底**，否则起始高度异常（落点被顶到高空）时包围盒不够高，模型半截被裁。
- **剔除距离 128 格（`16384 = 128²`）**：默认 `Projectile` 的 0.5 格包围盒 + 默认剔除距离会让
  「远处看不见、走近突然出现整片」；这里的大范围特效必须自己覆写（§14.51 ⑧）。

**一句话**：先数「一个目标会被判几次」，再选形态；A 用位图、B 用 Set、C 不用；
时间源按「要准时还是要总量」选；三种形态的结算都必须固定间隔、绑定施法者、只存推不出来的量。
